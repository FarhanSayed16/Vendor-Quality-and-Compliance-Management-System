Relational Normalization Journey (1NF $\to$ 3NF/BCNF)

Eliminating insertion, update, and deletion anomalies across the automotive supply chain

1NF: Atomic Attributes 100% Atomic

Eliminated multi-valued comma lists (e.g., storing multiple defect types in one inspection row). Decomposed composite delivery addresses into atomic columns (city, country). Every table has a distinct single-column surrogate Primary Key.

2NF: No Partial Dependencies Full Dep

Decomposed purchase orders into purchase_orders and po_line_items. In composite keys, non-key attributes (unit_price, ordered_quantity) depend strictly on the complete line-item key, not just the order header.

3NF / BCNF: No Transitives Candidate Keys

Eliminated transitive relationships where non-key attributes determined other non-keys. Extracted contract terms (max_allowable_ppm, hourly_downtime_penalty) into supplier_contracts. Every determinant is a candidate key.

Professor Viva Defense Cheat-Sheet

High-probability theoretical and implementation questions evaluated by DBMS professors. Click each card to reveal the recommended senior-level model answer and technical talking points.

1 Why did you choose 3NF/BCNF normalization over a denormalized star schema? ▸
Key Senior Examiner Concept: OLTP transactional integrity vs OLAP analytical reads. Quality management requires zero data corruption.

Model Answer: In an automotive quality management system, data integrity is paramount. If we used a denormalized schema, updating a supplier's compliance score or hourly penalty rate would require modifying thousands of historical inspection records—risking severe Update Anomalies where different rows report conflicting penalty amounts.

By normalizing to 3NF and BCNF:

  • Every non-key attribute depends strictly on the primary key (no transitive dependencies like supplier country determining penalty terms).
  • Every determinant is a candidate key (BCNF guarantee).
  • Insertion anomalies are prevented (we can register a new Tier-1 supplier before they ship their first batch).
  • Deletion anomalies are prevented (deleting a canceled purchase order does not erase the component catalog entry).

To maintain fast read performance for executive dashboards, we built pre-joined SQL views (v_supplier_quality_scorecard, v_financial_recovery_summary) with 10 targeted B-Tree indexes.

2 Why use database triggers for PPM calculation and audit logging instead of application code? ▸
Key Senior Examiner Concept: Centralized single-source-of-truth vs distributed fragile client logic.

Model Answer: Automotive manufacturing involves multiple heterogeneous client systems: plant-floor barcode scanners, automated testing rigs, Java microservices, and mobile audit tablets. If PPM calculation or audit logging were handled in application code, a developer writing a new ETL script or a buggy batch-import tool could bypass the business logic, resulting in un-audited or un-scored lots.

By implementing trg_auto_calculate_ppm and trg_audit_quarantine_insert at the database engine level:

  • Zero Bypass: Any insertion into inspection_records immediately computes PPM via engine arithmetic regardless of which programming language or client executed the INSERT.
  • Regulatory Compliance: IATF 16949 / ISO 9001 auditors require proof of an immutable audit trail that application users cannot manipulate or skip.
3 How does your system guarantee ACID properties during simultaneous assembly line stoppages? ▸
Key Senior Examiner Concept: Transaction isolation, foreign key cascading, and write-ahead logging (WAL).

Model Answer:

  • Atomicity: When an inspection fails and triggers a quarantine hold plus a debit memo, all operations execute within an atomic transaction. If debit memo creation fails, the quarantine record rolls back to prevent inconsistent states.
  • Consistency: Enforced by domain CHECK constraints (defect_count <= sample_size, hourly_downtime_penalty >= 0.00) and strict FOREIGN KEY ... ON DELETE RESTRICT rules preventing orphaned records.
  • Isolation: Both SQLite (via WAL journal) and PostgreSQL (via MVCC Multi-Version Concurrency Control) ensure readers never see uncommitted quarantine transitions, preventing dirty reads.
  • Durability: Transactions are committed to non-volatile disk storage before confirming execution success to the calling client.
4 Explain how the Window Function in Query 6 (DENSE_RANK) solves a business problem. ▸
Key Senior Examiner Concept: CTE aggregation combined with partitioned window ranking without collapsing rows.

Model Answer: A standard ORDER BY component_ppm DESC mixes Tier A safety parts (crankshafts) with Tier C fasteners, hiding which critical parts pose high safety risks.

In Query 6, we use: 

DENSE_RANK() OVER (PARTITION BY criticality_tier ORDER BY component_ppm DESC) AS defect_rank_within_tier

This partitions the catalog into Tier A, B, and C pools and assigns seamless ranks (1, 2, 3...) within each tier without gaps. This instantly isolates the highest-risk safety component (BorgWarner Turbo Actuator at Rank 1 in Tier A with 70,000 PPM) without requiring separate complex subqueries for each tier.

5 How will this architecture scale when processing 10,000,000 inspection records annually? ▸
Key Senior Examiner Concept: B-Tree indexing, range partitioning by date, and materialized view caching.

Model Answer:

  • Targeted B-Tree Indexes: We created 10 B-Tree indexes on high-cardinality search columns (idx_receipts_lot, idx_inspections_date, idx_inspections_status) converting full table scans ($O(N)$) into logarithmic lookups ($O(\log N)$).
  • Range Partitioning by Date: In PostgreSQL, inspection_records is partitioned by inspection_date monthly. Queries filtering for recent batches prune 95% of partitions instantly.
  • Materialized Views: Heavy analytical joins across 6 tables are cached in scheduled materialized views, refreshed off-peak, ensuring sub-50ms dashboard response times.
